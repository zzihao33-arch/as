# TYG 已确认接口的部署与验收

测试发布分支为 `codex/tyg-test-deployment`，基于当前 `staging` 合并本地开发分支 `codex/tyg-confirmed-api`。本变更尚未部署测试或正式环境，未进行真实 MySQL/COS 压测及 TYG 双方联调。

## 部署配置

1. 测试环境先备份并执行迁移 `016_add_label_retention.sql`。新服务启动时检查这两个字段；未迁移时拒绝启动。本次仅授权测试环境部署；正式发布仍需独立验收和授权。
2. MySQL 需为 8.0.13 或更新版本。旧记录按原文件就绪时间加七天回填；老文件可能在首次更新后立即过期。迁移的默认表达式覆盖发布交接期间旧程序的新增记录。
3. 配置 `INBOUND_BATCH_JSON_LIMIT=32mb`、`SHIPMENT_JSON_LIMIT=32mb`、`LABEL_PDF_LIMIT=20mb`。Nginx 模板上限已调整为 `32m`。实际服务器需安装并检查对应模板；仅拉取代码不会自动改变已经安装的 Nginx 配置。
4. 确认 TYG 测试 Key 同时拥有 `shipments:write`、`labels:write`、`shipments:read`。生产配置中的测试实例可能按原鉴权策略使用安全签发的 live 格式 Key，不能仅凭密钥前缀判断它对应哪个环境。
5. 按 `tyg-label-retention.md` 核对私有 COS 的 `test/labels/` 七天生命周期、无效文件清理和删除权限。每个进程每分钟触发到期清理，每次最多处理 100 条；多进程用数据库锁互斥。COS 请求超时设置为 20 秒。

## 功能验收

使用独立测试批次验证：预报空数组、两票含 Base64 推送、同键重试、同键修改拒绝、PDF 替换、转单号变更、提单到仓后补传、不同客户归属冲突、存储失败和数据库提交失败。确认仓库端只能看到同一事务提交的单号关系与当前面单。

验证七天到期后下载和打印被拒绝，当前指针失效会同步到仓库。模拟对象删除失败及重传竞争，确认元数据保留且新版本不被旧清理任务删除。幂等重放返回历史响应，新业务键重传才会续期。

## 大批量测试

服务部署后，在受控测试环境设置 `TYG_TEST_API_KEY`，使用代表性真实 PDF。该工具不会读取 `.env`，只允许本地回环地址或指定测试域名；拒绝正式域名及重定向。

从 `services/cloud-api` 目录运行：

```bash
npm run load:tyg:test -- --target https://api-test.cmhubtool.com --labels 10000 --batch-size 50 --concurrency 2 --pdf /secure-test-fixtures/representative-label.pdf
```

先小批次验证再增加到几万单，并按 PDF 文件大小保持请求在 32 MiB 以下。工具报告请求数、可靠接收面单数、失败码、总耗时、吞吐和请求延迟 P95。成功必须同时返回正确的 `shipmentCount` 与 `labelCount`，不会把旧版仅保存映射的响应计为完整面单成功。

未提供 PDF 文件时只使用极小合成内容验证传输流程，不能据此证明真实面单性能。几万单尽量在十分钟内完成是测试环境目标；结果需同时记录服务版本、数据规模、PDF 大小分布、限流参数、并发、内存峰值和错误率。

## 发布判定

只有测试版本通过功能、存储保留、性能和 TYG 联调验收后，才生成正式 v1.0 PDF，并按用户明确授权发布被验收的提交。原有正式部署流程的迁移、健康检查和回滚问题仍需在正式发布前解决。

## 与现有测试分支合并

保留既有迁移 013–015，新增保留期迁移顺延为 016，索引名与旧版本分开。早期 `/api/v1/air-shipments`、`/api/v1/label-pushes` 路由仍保留旧字段、5 MiB 单文件限制及版本响应；面单写入改用同一持久化和过期机制，Base64 不进入数据库。旧幂等响应保持兼容。测试分支原有客户资料、提货文档及仓库功能一并保留。
