# TYG 系统对接工作总结与当前进度

> 更新日期：2026-08-31  
> 当前阶段：业务合同已确认，API 尚未开发部署  
> 用途：上下文交接、内部技术评审和下一轮实施依据

## 1. 当前结论

TYG 对接已从最初的“三字段单票推送”调整为完整的两层业务模型：

1. TYG 先推送空运提单预报；
2. 再通过一个统一接口逐票推送该提单下的原单号、转单号和 PDF Base64。首次面单、迟到补传、同转单号换 PDF、转单号更新全部使用同一接口。

本轮已完成业务规则逐项确认，并将客户评审合同更新为“两接口”方案。新接口尚未写入后端代码，也尚未部署测试环境。现有生产实现仍然是旧的“批次 JSON + 原始 PDF 上传”流程，不能把新文档描述成已经上线或可联调。

## 3. 已确认的核心业务决策

### 3.1 接口结构

#### 接口一：空运提单预报

```http
POST /api/v1/air-shipments
```

请求字段：

```json
{
  "airWaybillNo": "180-98109734",
  "forecastCartons": 120,
  "forecastPackages": 50000,
  "forecastWeight": 1850.5,
  "weightUnit": "KG"
}
```

业务规则：

- `forecastCartons` 是预报总箱数。
- `forecastPackages` 是预报总包裹数/票数。
- `forecastWeight` 是整张空运提单的预报总重量。
- `weightUnit` 第一阶段支持 `KG` 和 `LB`。
- 仓库开始收货前，TYG 可以更新预报字段，系统保留修改审计。
- 仓库开始收货后，预报字段锁定，返回 `AIR_SHIPMENT_LOCKED`。
- 仓库实收箱数、实收包裹数和实收重量只能由 CM-HUB 仓库流程记录。

#### 接口二：统一逐票面单推送

```http
POST /api/v1/label-pushes
```

请求字段：

```json
{
  "airWaybillNo": "180-98109734",
  "originalTrackingNo": "HHWV06218005702YQ",
  "transferTrackingNo": "9400111899560000000000",
  "labelBase64": "JVBERi0xLjcKJc..."
}
```

业务规则：

- 必须先成功创建空运提单，找不到时返回 `AIR_SHIPMENT_NOT_FOUND`，不暂存孤立面单。
- 每次请求只接收一票包裹和一份 PDF。
- `replacementReason` 为可选字段；未提供时由系统记录默认更新原因。
- 首次面单、迟到补传、同转单号换 PDF 和转单号更新全部调用本接口。
- `labelBase64` 是纯标准 Base64，不带 `data:application/pdf;base64,` 前缀。
- 仅接收 PDF，不接收 JPG、PNG、HTML 或第三方 URL。
- 原始 PDF 最大暂定 5 MiB，完整 JSON 最大暂定 7 MiB。
- 只有单号关系和 PDF 均可靠保存后才返回 HTTP 200 和 `SUCCESS`。
- 同原单号、同转单号、同 PDF：按重复请求成功返回，不创建新版本。
- 同原单号、同转单号、不同 PDF：创建新版本并设为当前有效。
- 同原单号由 A→B 更新为 A→C：C 未绑定其他原单号时，原子更新关系和 PDF 版本；B 和旧 PDF 失效但保留审计。
- C 已绑定其他原单号时返回 `TRACKING_ALREADY_BOUND`，不得覆盖。
- 原单号不得通过本接口自动移动到另一张空运提单。
- 旧面单已经打印时，CM-HUB 设置重新打印提醒。
- 空运提单到仓或关闭后仍允许首次面单、迟到补传和更新，并记录 `latePush`。
- 第一阶段不提供 TYG 状态查询或处理结果回调。

### 3.2 幂等、冲突和唯一性

- 完全相同的数据允许重复推送，仍返回成功并标记 `duplicate: true`。
- 两个 POST 接口都要求 `Idempotency-Key`；同键同报文返回原结果，同键不同报文返回 `IDEMPOTENCY_CONFLICT`。
- 每个真实业务版本使用新幂等键；网络重试复用原键和原报文，旧请求不得换新键重发。
- 同一原单号的多个业务版本必须由 TYG 顺序推送并等待前一版本成功；第一阶段暂不要求 `labelRevision`。
- 原单号和转单号在 TYG 客户范围内保持唯一。
- 原单号已属于另一张空运提单时，返回 `TRACKING_ALREADY_BOUND`。
- 转单号已绑定另一原单号时，返回 `TRACKING_ALREADY_BOUND`。
- 相同原单号、相同转单号但 PDF 不同时，统一接口直接创建新版本。
- 相同原单号、转单号变化时，统一接口在无冲突的前提下直接版本化更新。
- 任何更新都不得自动改变包裹所属空运提单。

### 3.3 包裹统计和差异

- 有效包裹数按唯一 `originalTrackingNo` 统计。
- 完全重复请求不增加包裹数。
- 换 PDF 和转单号更新版本不增加包裹数。
- 提单关闭后新增的唯一原单号正常增加包裹数。
- 少于预报包裹数：显示未收齐和缺少数量。
- 等于预报包裹数：显示面单已收齐。
- 超过预报包裹数：继续接收有效面单，同时显示差异和异常提醒。

### 3.4 成功和错误响应

成功格式：

```json
{
  "code": "SUCCESS",
  "message": "接收成功",
  "data": {
    "duplicate": false
  },
  "requestId": "TYG-20260831-000001"
}
```

失败格式：

```json
{
  "code": "INVALID_LABEL_PDF",
  "message": "labelBase64 解码后不是完整的 PDF 文件",
  "requestId": "TYG-20260831-000002"
}
```

主要错误码：

- `VALIDATION_ERROR`
- `INVALID_BASE64`
- `INVALID_API_KEY`
- `AIR_SHIPMENT_NOT_FOUND`
- `AIR_SHIPMENT_LOCKED`
- `IDEMPOTENCY_KEY_REQUIRED`
- `IDEMPOTENCY_CONFLICT`
- `TRACKING_ALREADY_BOUND`
- `PAYLOAD_TOO_LARGE`
- `UNSUPPORTED_MEDIA_TYPE`
- `INVALID_LABEL_PDF`
- `RATE_LIMITED`
- `INTERNAL_ERROR`

### 3.5 安全

- 仅允许 HTTPS。
- 使用 TYG 专属 `X-API-Key`。
- 测试和生产使用不同 API Key。
- API Key 只允许保存在 TYG 服务端，不允许进入 URL、浏览器、移动端、截图或普通日志。
- 日志不得记录完整 API Key、完整 Base64 或面单个人信息。
- TYG 如有固定出口 IP，可在联调后增加 IP 白名单。

### 3.6 数据保存期限

- 每个 PDF 版本从成功接收起保存 7×24 小时。
- 7 天内仓库可以在 CM-HUB 内部查看和重新打印。
- 7 天后自动删除 PDF，不长期保存完整 Base64。
- 空运提单号、原单号、转单号、PDF 哈希、接收时间、版本和审计记录保留 2 年。
- PDF 删除后，TYG 重新推送完全相同数据时，允许重新保存并重新计算 7 天保存期。

### 3.7 容量和重试

第一阶段对外约定：

- 每分钟 1,200 次请求；最终以联调配置为准。
- 建议 TYG 客户端并发不超过 20。
- 5 万票按初始限流约需 42 分钟。
- 返回 HTTP 429 时，TYG 按 `Retry-After` 降速和重试。
- 网络超时、429、500、503 可以使用完全相同内容重试。
- 建议最多重试 5 次，间隔 1、2、4、8、16 秒并加入随机抖动。

内部后续容量目标：

- 持续每秒约 100 票；
- 5 万票目标在 10 分钟内可靠接收；
- 在 TYG 真实 PDF 大小、网络和生产配置下压测通过前，不向客户承诺该 SLA。

## 4. 当前未完成事项

- OpenAPI 尚未增加两个新接口和 Schema。

- 当前面单存储实现主要是本地文件系统模型，不足以直接支撑多实例横向扩容和每秒 100 票目标。
- PDF 7 天清理任务尚未实现。
- 1,200 次/分钟的第一阶段容量和每秒 100 票的后续目标均未压测。
- 测试环境地址、测试 API Key 和生产 API Key 尚未交付。
- v1.1 客户评审稿 DOCX 已重新生成并落盘；仍需在实现完成后发布正式版。
