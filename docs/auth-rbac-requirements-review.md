## 0. 评审结论

该需求方向正确，但不应按原稿直接开发。CM-HUB 已经具备仓库用户、仓库成员关系、三级角色、8 小时安全会话、成员管理 API 和服务端角色校验，因此本项目应定义为：

> 在现有仓库身份体系上补齐账户生命周期、统一权限目录、角色模板、后台管理页面、密码生命周期和安全审计。

原稿中以下规则需要修改后才能进入开发：

1. 不开放前台自助注册；“账号注册”统一改称“管理员开通账户”。
2. 不在前端保存 JWT；继续使用现有 `HttpOnly + Secure + SameSite=Strict` 的不透明会话 Cookie。
3. 不使用手机号后 6 位作为初始密码；改为一次性强随机临时密码。
4. 登录请求不自动重试 3 次，避免一次点击生成多个会话并放大锁定计数。
5. 离职账户和无用角色允许永久删除，不设置归档状态；但物流单据、打印事实等业务记录不能随账号一起级联删除。
6. 角色权限必须由服务端校验，隐藏菜单和按钮仅用于界面呈现，不能代替授权。
7. “主管审批特殊操作”尚未定义具体动作，不能直接建设通用审批引擎。
8. 权限系统本身不会自动让本机数据跨电脑共享；本期已另行实现共享扫码批次和全局拦截，BOL 与薪酬仍保持浏览器本地数据。

## 2. 建议采用的领域模型

### 2.1 身份和授权对象

| 名称 | 定义 | 关键边界 |
| --- | --- | --- |
| 仓库用户 | 一个自然人的全局登录身份 | 不是上游客户，不持有上游 API Key |
| 仓库成员关系 | 用户加入某个仓库的授权关系 | 保存工号、所属仓库、运营角色和成员状态 |
| 系统管理员 | CM-HUB 内部的全局管理身份 | 管理账户、角色、权限和安全审计；不等于上游客户管理员 |
| 运营角色 | 分配给仓库成员关系的一套权限模板 | 一个成员关系在同一时间只绑定一个运营角色 |
| 权限点 | 服务端可判定的最小业务动作 | 使用稳定代码，例如 `scan.print`，不直接使用菜单名称 |
| 会话 | 用户一次已认证的浏览器登录 | 与工作站不同；会话是凭据，工作站是审计对象 |
| 工作站 | 当前仓库电脑的浏览器安装实例 | 不用于登录，不持有上游 API Key |
| 上游客户 | 通过服务器 API 推送物流数据的外部组织 | 与仓库用户、角色和员工账号完全分离 |

### 2.2 建议的角色范围

- `SYSTEM_ADMIN`：全局管理角色。负责账户、仓库成员、角色模板、权限和安全审计。
- `SUPERVISOR`：仓库运营角色。负责现场异常处理和主管级功能。
- `OPERATOR`：仓库运营角色。负责扫码、换单和被授权的日常任务。
- 自定义运营角色：由系统管理员创建，供特殊岗位使用，例如 BOL 文员或薪酬专员。

同一个仓库用户可以加入多个仓库，并在不同仓库拥有不同运营角色。系统管理员身份与运营角色分开；系统管理员参与扫码时仍需选择一个仓库和工作站，以保证打印审计归属明确。

## 4. 权限模型

### 4.1 基本原则

1. 默认拒绝：没有明确权限即不可执行。
2. 服务端为最终权限边界；前端必须同时控制菜单、路由和按钮。
3. 权限不写入长期有效 JWT，避免角色修改后旧令牌继续越权。
4. 每个受保护接口必须声明一个或多个权限点并具备自动化授权测试。
5. 系统管理员操作同样写入审计日志，不允许绕过审计。
6. 现有全局上游数据可见性不变：具有 `shipments.view` 的有效仓库成员可读取全部上游物流单据。

## 5. 页面与交互需求

### 5.1 登录页 `/login`

页面目标：完成内部仓库人员身份验证。该路由必须独立存在，不再只是任意业务路由上的登录遮罩。

- 建议登录字段：登录账号、密码；不再要求仓库代码和邮箱。
- 登录账号全局唯一、大小写不敏感，建议限制为 4–50 字符，并只允许字母、数字、点、下划线和短横线。
- 默认勾选“记住账号”；只保存登录账号，不保存密码、Cookie 内容或任何令牌。
- 密码最大 256 字符；支持回车提交。
- 登录失败统一显示“账号或密码错误”，不得暴露账户是否存在、被禁用或属于哪个仓库。
- 达到安全限制时显示“登录尝试过于频繁，请稍后重试”。
- 网络失败显示“无法连接服务器，请检查网络后重试”，登录请求不自动重试。
- 右下角显示前端版本和构建标识，便于排障。
- 首次登录或密码被重置后，只能进入修改密码流程，完成前不加载业务页面。
- 用户只有一个有效仓库成员关系时直接进入该仓库；存在多个成员关系时，认证成功后进入仓库选择页。
- 全局系统管理员可直接进入管理后台；需要参与扫码时，再选择一个仓库和工作站作为操作审计上下文。

### 5.2 工作台 `/dashboard`

沿用现有 `/dashboard` 作为登录后首页，不新增含义重复的 `/home`。

- 菜单根据服务端返回的权限点动态渲染。
- 直接输入无权路由时显示 403 页面并提供返回入口，不能只靠隐藏菜单。
- 用户区显示姓名、当前仓库、运营角色。
- 用户菜单包含修改密码、退出当前会话；系统管理员额外显示系统管理入口。
- 权限集在页面重新获得焦点、收到 403 或定期刷新时重新获取。

### 5.3 账户管理 `/admin/accounts`

- 仅 `accounts.view` 可访问；所有写操作需对应管理或重置密码权限。
- 搜索关键字覆盖姓名、工号、邮箱、手机号；角色、状态和仓库使用精确筛选。
- 默认每页 20 条，服务端分页；搜索输入防抖，不能把全部账户下载到浏览器后筛选。
- 表格按“成员关系”展示：姓名、工号、邮箱、手机号、仓库、运营角色、状态、最近登录时间。
- 支持创建账户、编辑资料、添加仓库成员关系、调整角色、启用/禁用和重置密码。
- 支持永久删除离职账户；删除前必须二次确认、撤销全部会话并解除成员关系。
- 系统拒绝停用最后一个有效系统管理员，并防止管理员在当前会话中误停用自己。

### 5.4 新建或编辑账户抽屉

建议字段：

| 字段 | 规则 |
| --- | --- |
| 姓名 | 必填，1–128 字符 |
| 登录账号 | 必填，全局唯一、大小写不敏感；创建后只允许系统管理员修改 |
| 工号 | 必填，在所属仓库内唯一 |
| 邮箱 | 可选，填写时必须格式合法且全局唯一；作为联系资料，不是登录标识 |
| 手机号 | 可选，标准化保存；不用于生成密码 |
| 仓库 | 必填；系统管理员可为现有用户增加成员关系 |
| 运营角色 | 必填且必须为有效角色 |
| 状态 | 新建默认启用 |

若登录账号已存在，不得创建第二个身份或覆盖原账户密码。系统管理员可以在明确确认后把现有用户加入另一个仓库。

### 5.5 角色配置 `/admin/roles`

- 默认角色与自定义角色分区展示。
- 角色卡展示名称、描述、状态、关联成员数和最后修改时间。
- 角色名称 1–20 字，全局唯一；角色代码由系统生成，不允许随意修改。
- 默认运营角色和自定义角色都可以永久删除，不设置归档状态。
- 任何角色只有在关联成员数为 0 时才能删除；有关联成员时必须先批量重新分配。
- 删除默认 `OPERATOR` 前必须指定新的默认运营角色；删除 `SUPERVISOR` 前必须确认所有主管成员的替代角色。
- 全局 `SYSTEM_ADMIN` 是平台管理授权，不是普通运营角色模板；最后一个有效系统管理员不可删除或移除。
- 删除前把角色名称和权限快照写入安全审计；角色代码删除后仍不允许复用，避免历史审计含义变化。
- 权限树按模块分组。父级勾选可批量选中子项，但最终保存的是具体权限点。
- 保存前展示新增和移除权限的差异；高风险权限单独提示。

### 5.6 安全审计 `/admin/audit`

- 支持按时间、操作人、目标账户、事件类型和结果筛选。
- 记录账户创建/编辑/禁用/启用、角色分配、密码重置、角色权限修改、会话撤销和管理员解锁。
- 每条记录包含操作人、目标对象、脱敏前后差异、IP、User-Agent、请求 ID、时间和结果。
- 不记录明文密码、临时密码、Cookie、会话令牌或上游 API Key。
- 审计日志不可由普通管理员在产品内删除。

## 6. 认证与会话规则

### 6.1 登录安全

- 继续使用密码哈希，不保存或记录明文密码。
- 对 IP + 标准化登录账号执行限流，避免攻击者通过反复尝试把某一员工账号永久锁死。
- 建议规则：10 分钟内超过 10 次尝试时限制该 IP + 登录账号组合 30 分钟；成功登录后清理对应失败计数。
- 若未来需要全账号锁定，必须先增加管理员解锁、安全告警和防恶意锁号策略，再单独评审。
- 所有无效凭据、禁用账户、禁用仓库或无效成员关系统一返回相同的 401 业务错误。

### 6.2 会话保持与续期

- 登录成功由服务端设置不透明的 HttpOnly Cookie，前端 JavaScript 不读取令牌。
- 普通会话有效期 8 小时。
- 距离过期 30 分钟时提示用户续期；确认后调用续期接口，服务端旋转令牌并撤销旧令牌。
- 建议单次登录最长连续会话为 16 小时，之后必须重新输入密码。
- 账户全局禁用、成员关系禁用、密码重置后，相关有效会话立即撤销。
- 角色权限修改不依赖重新登录；服务端下一次请求立即按新权限判定。

### 6.3 密码生命周期

- 新账号和管理员重置密码时，由服务端生成至少 20 字符的强随机临时密码，只展示一次。
- 临时密码必须在首次成功验证后立即更换，业务接口在更换前统一拒绝。
- 用户新密码建议为 12–128 字符，拒绝常见弱密码；不强制无意义的固定字符组合。
- 修改密码需要输入当前密码；修改成功后撤销其他会话，当前会话可安全轮换。
- 管理员看不到用户现有密码，也不能直接指定长期密码。

### 6.4 登出

- 登出必须先由服务端撤销当前会话，再清理本机用户缓存并跳转 `/login`。
- 服务端已不可用或会话已失效时，仍需完成本机清理。
- 退出账号不删除当前工作站的业务缓存；换人登录后按权限重新加载界面。

## 7. 账户生命周期规则

| 状态 | 是否可登录 | 说明 |
| --- | --- | --- |
| `ACTIVE` | 是 | 正常账户 |
| `PASSWORD_CHANGE_REQUIRED` | 仅可进入改密流程 | 新建或重置密码后的过渡状态 |
| `DISABLED` | 否 | 离职、安全风险或管理员停用 |

- 仓库成员状态与用户全局状态分离：停用某一仓库成员关系不应自动停用该用户在其他仓库的身份。
- 系统管理员才能执行用户全局禁用；仓库层面的运营管理只影响成员关系。
- 禁用、密码重置和角色变更必须记录原因。
- 离职员工可永久删除登录身份、密码、联系方式和成员关系，不设置归档账户。
- 删除前必须撤销全部会话，并把仍需保留的业务事实改为匿名主体引用，例如“已删除员工 #A17F”。
- 删除员工不得级联删除物流单据、打印提交、拦截命中等业务事实，否则系统会失去包裹追溯能力。

## 8. 权限即时生效规则

1. 服务端每次请求都必须检查用户状态、仓库成员状态和当前权限版本。
2. 权限变更保存后，服务端立即按新权限授权；旧会话不得继续使用已撤销权限。
3. 前端最迟在 60 秒、重新聚焦窗口或收到 403 时刷新权限集并重新渲染菜单。
4. 账户禁用或密码重置不等待前端刷新，直接撤销相关会话。
5. 角色可永久删除；关联成员的 `roleId` 会置空、现有会话立即失效，重新分配角色前禁止登录。

## 9. 建议 API 合同

以下为产品级接口清单，具体请求响应在开发前另写 OpenAPI：

| 路径 | 方法 | 说明 |
| --- | --- | --- |
| `/warehouse/v1/sessions` | POST | 登录并设置会话 Cookie；沿用现有接口 |
| `/warehouse/v1/session` | GET/DELETE | 恢复或注销当前会话；返回权限集 |
| `/warehouse/v1/session/renew` | POST | 在允许窗口内旋转并续期会话 |
| `/warehouse/v1/session/password` | POST | 修改当前用户密码 |
| `/warehouse/v1/accounts` | GET/POST | 查询或创建账户/成员关系 |
| `/warehouse/v1/accounts/{userId}` | PATCH/DELETE | 编辑资料、全局状态或永久删除账户 |
| `/warehouse/v1/accounts/{userId}/role` | PUT | 新增或替换仓库成员角色 |
| `/warehouse/v1/accounts/{userId}/reset-password` | POST | 生成一次性临时密码并撤销会话 |
| `/warehouse/v1/roles` | GET/POST | 查询或创建角色模板 |
| `/warehouse/v1/roles/{roleId}` | PATCH/DELETE | 按版本编辑或永久删除角色 |
| `/warehouse/v1/security-audit` | GET | 查询身份与权限审计 |

所有修改接口必须校验精确 Origin、有效会话和权限点，并记录幂等请求标识或请求 ID。不存在面向浏览器的上游 API Key 入口。

## 10. 数据需求

产品模型至少需要支持：

- 用户：登录账号、姓名、邮箱、手机号、全局状态、密码状态、最近登录和密码修改时间。
- 成员关系：仓库、工号、运营角色、成员状态。
- 角色模板：名称、描述、系统/自定义标记和并发控制版本。
- 权限目录：稳定权限代码、所属模块、展示名称和风险等级。
- 角色权限关系：角色与权限的多对多关系。
- 会话：用户、仓库、工作站、过期时间、撤销时间、创建 IP 和 User-Agent。
- 安全审计：事件类型、操作人、目标、脱敏差异、请求信息、结果和时间。

数据库设计必须保留现有打印审计对用户和仓库的引用，不得通过级联删除破坏历史记录。

## 11. 异常和边界场景

1. 最后一个系统管理员不能禁用、删除或移除自身管理员身份。
2. 管理员重置某用户密码后，该用户所有电脑上的现有会话立即失效。
3. 用户在 A 仓库被禁用，但在 B 仓库仍为有效成员时，B 仓库登录不受影响。
4. 用户正在扫码时角色被收回 `print.submit`，下一次打印请求必须被服务端拒绝，前端刷新权限并提示联系管理员。
5. 已缓存到本机的 PDF 可能仍存在于浏览器存储；RBAC 可阻止产品继续下载和提交审计，但不能替代仓库电脑的操作系统安全管理。
6. 角色仍关联成员时允许在二次确认后删除；系统必须显示受影响人数，并明确这些员工会被退出且在重新分配前不能登录。
7. 网络超时的登录请求不自动重试；用户再次提交前，客户端先尝试恢复可能已经建立的 HttpOnly 会话。
8. 管理员调整权限时两人同时编辑同一角色，应使用版本号防止后保存者静默覆盖前者。
9. 前端隐藏无权按钮后，手工调用接口仍必须得到 403，且产生拒绝审计或安全指标。
10. 上游 API Key 泄露或失效不影响仓库用户密码；两套身份生命周期完全独立。

## 12. 验收标准

### 12.1 功能验收

- 新员工只能由系统管理员开通，产品不存在公开注册入口。
- 新账号使用一次性随机密码首次登录，并在改密完成前无法进入业务模块。
- 无权限菜单不显示，直接访问路由得到 403，对应服务端接口同样返回 403。
- 账户禁用、密码重置和成员禁用能使目标会话立即失效。
- 角色权限保存后，目标用户无需重新登录即可在下一次请求中获得新权限。
- 默认角色和自定义角色都可永久删除；关联成员会被退出并进入未分配角色状态，安全审计保留删除时的角色与权限快照。
- 所有账户、角色、权限和密码管理操作都有完整、脱敏、不可由普通管理员删除的审计记录。
- 所有有效且具有 `shipments.view` 的仓库成员继续共享全部上游物流数据。

### 12.2 安全验收

- 浏览器本地存储中不存在密码、JWT、会话令牌或上游 API Key。
- 100% 受保护的服务端路由声明权限要求并具有允许/拒绝自动化测试。
- 100% 高风险管理操作记录操作人、目标、结果、IP、请求 ID 和时间。
- 401 登录错误不泄露账号是否存在、是否禁用或是否属于指定仓库。
- 系统无法通过管理页面移除最后一个有效系统管理员。

### 12.3 效率指标

原稿“耗时降低 50%”缺少现状基线，无法直接验收。建议改为：

- 管理员创建一个账号并分配角色的人工操作时间不超过 2 分钟。
- 修改一个角色权限并确认生效的人工操作时间不超过 3 分钟。
- 正常网络下登录接口 P95 不超过 2 秒。
- 上线 30 天内，100% 在岗仓库员工使用独立账户，不再共用管理员账号。
- 上线 30 天内，已确认的未授权操作事件为 0；权限拒绝和管理操作可完整追溯。

## 13. 建议实施顺序

1. 确认本评审稿中的待决策项和默认权限矩阵。
2. 固化领域词汇与权限代码，形成数据库迁移和 OpenAPI 设计。
3. 先实现服务端权限、密码生命周期和审计，再实现管理页面。
4. 用兼容权限映射迁移现有管理员和账号，确保扫码业务不中断。
5. 在本地和测试环境完成角色切换、会话撤销、直接接口越权和并发编辑测试。
6. 经用户明确授权后才提交、推送和发布生产。

### 14.1 D1 已确认登录流程

```text
输入登录账号 + 密码
  → 校验全局用户身份
  → 首次登录则强制修改临时密码
  → 只有一个有效仓库：直接进入工作台
  → 有多个有效仓库：选择本次工作仓库
  → 系统管理员：可进入管理后台；做现场作业前选择仓库
```

该方案把“人是谁”和“本次在哪个仓库作业”分开。员工调仓或同时负责多个仓库时，不需要为同一个人创建多个登录账号。

### 14.2 D6 删除语义

不设置“已归档员工”或“已归档角色”列表。删除是永久操作：

1. 离职员工删除后，登录身份、密码、姓名、邮箱、手机号和成员关系永久移除，无法恢复。
2. 删除员工前撤销全部会话，并解除其角色和仓库关系。
3. 物流单据、打印提交、拦截命中等业务事实不随员工删除；其中的操作者改为不可反查个人信息的“已删除员工 + 随机引用”。
4. 默认 `OPERATOR`、`SUPERVISOR` 和自定义角色均可永久删除。
5. 删除角色时允许把关联成员的 `roleId` 置空，但必须撤销其会话并禁止其登录，直至重新分配角色。
6. 删除默认操作员角色后，新建账号必须显式选择其他现有角色；系统不自动继承已删除角色的权限。
7. 最后一个有效 `SYSTEM_ADMIN` 授权始终受保护；其他系统管理员账户可以删除。
8. 删除角色时，安全审计保留当时的角色名称和权限快照，但不保留可再次启用的角色记录。

该方案不是账户归档。它只把已经发生的包裹处理事实与离职员工个人资料解耦，避免删除一个员工时连带抹掉“某张面单曾在哪台电脑提交打印”这类业务记录。

### 14.3 D7 跨电脑共享具体指什么

跨电脑共享主要指仓库作业过程中产生或维护的业务状态，而不是把每一种浏览器设置都上传云端。本轮已经确认两个核心场景：共享导入扫码、共享拦截。

| 数据类别 | 当前状态 | 是否已经跨电脑 | 需求结论 |
| --- | --- | --- | --- |
| 上游物流单据、云端 PDF 面单 | 云端 MySQL + 私有文件存储 | 是 | 保持所有有权限仓库账号共享 |
| 仓库账号、角色、权限、会话 | 云端身份系统 | 是/本需求补齐 | 必须云端共享 |
| 打印提交事实 | 已写入云端 `print_attempts` | 写入已共享，前端尚缺完整查询页 | P0 补齐跨电脑打印历史查询 |
| 全局拦截条目 | 当前浏览器本地 | 否 | P0 云端共享；A 导入后 B 必须立即生效 |
| Excel/PDF 作业批次 | 当前浏览器 IndexedDB | 否 | P0 云端共享；A 导入后 B 自动获得同一映射和面单 |
| 单号扫描、占用和处理状态 | 主要在当前浏览器 | 否 | P0 云端共享并提供并发防重，否则 A、B 可能重复打印 |
| 临时页面日志 | 当前浏览器 | 否 | 仍可本地保存；关键业务事件写入云端 |
| BOL 记录 | 当前浏览器本地 | 否 | 是否云端共享另行确认 |
| 考勤薪酬草稿与历史 | 当前浏览器本地 | 否 | 单独立项评审权限、隐私和保留周期 |
| 打印机、音效、QZ 连接设置 | 当前工作站本地 | 不需要 | 保持每台电脑独立设置 |

#### 14.3.1 共享导入扫码流程

```text
A 创建共享作业批次
  → 上传 Excel 和 PDF
  → 云端校验映射、文件和重复项
  → 批次完整后发布为 READY
  → A、B 等所有授权工作站自动同步
  → 任一工作站扫描时先向云端占用该单号
  → 占用成功才允许调用本机 QZ 打印
  → 打印提交结果同步给其他工作站
```

关键规则：

1. B 不需要再次导入 Excel 或 PDF；浏览器只下载本次扫描所需面单或按策略预缓存。
2. 批次处理完成前不对其他工作站发布，避免 B 使用不完整数据。
3. 同一单号同一时间只能被一个工作站取得短时作业占用；其他工作站看到“正在由某工作站处理”。
4. 占用在工作站崩溃或超时后自动释放；已提交打印的单号再次扫描需 `print.reprint` 权限。
5. 作业状态至少区分：待处理、处理中、已提交打印、失败、已拦截。
6. 所有状态记录账号、工作站和时间，A、B 可以看到同一批次的实时进度。
7. 共享模式无法连接云端时，主管或系统管理员可用 `offline_mode.enable` 为当前工作站开启单机应急模式；业务已确认不同电脑处理不同实体包裹，因此不把跨电脑重复占用视为阻断风险。
8. 可以同时存在多个 `READY` 批次；若同一扫描单号在多个活动批次中对应不同面单，系统必须阻断并要求明确选择，不能自动猜测。
9. 批次完成后由授权人员关闭；关闭后不再参与新扫描匹配，但既有打印事实继续保留。
10. 只有已完整缓存并通过哈希校验的映射和 PDF 才能离线打印；缓存缺失或损坏时仍然阻断。
11. 离线产生的打印事实先进入本机 outbox，恢复连接后使用原幂等标识回传，不得因回连而生成第二条打印事实。

#### 14.3.2 全局拦截同步流程

```text
A 导入或新增拦截单号
  → 云端校验并发布新拦截版本
  → B 等所有工作站同步最新版本
  → 扫描时先本机快速命中
  → 云端批准作业占用前再次执行最终拦截检查
```

关键规则：

1. 拦截条目是全局共享业务规则，不再属于某一浏览器。
2. 新增、批量导入、解除和修改原因都必须记录操作人、工作站和时间。
3. 即使 B 尚未完成本地同步，云端最终校验也必须阻止被拦截单号进入打印。
4. 云端或拦截数据不可用时采用 fail-closed：阻止打印并提示恢复连接，不允许静默跳过检查。
5. 拦截页面显示当前版本、最后同步时间和同步健康状态。

#### 14.3.3 实施优先级

1. **P0：共享导入批次 + 单号并发防重 + 全局拦截 + 云端打印历史**。
2. **P1：BOL 云端记录**，解决多电脑接续作业；是否纳入需另行确认。
3. **单独安全评审：考勤薪酬云端化**，因为涉及员工隐私和薪资数据。

#### 14.3.4 上游 API 数据共享边界

上游客户通过 API 推送并被 CM-HUB 接收的数据进入同一个全局仓内作业数据池：

```text
上游客户 C、T、Y、U、I 分别推送物流数据
  → CM-HUB 仍记录每条数据来自哪个客户
  → 所有具有 shipments.view 的 A、B、C、D 仓库员工共同查看和处理
  → 不建立“某客户只能由某员工或某仓库操作”的分配关系
```

具体规则：

1. 所有有效且具有 `shipments.view` 的仓库账号都能同步全部上游客户的物流单据和当前面单资产。
2. 扫码匹配默认搜索全部活动上游数据和共享作业批次，不要求操作员先选择客户。
3. 上游客户代码只用于标识数据来源、API Key 归属、幂等范围和结果回调对象，不是仓库权限边界。
4. 上游客户使用自己的 API Key 时仍然只能查询或修改自己的数据；“全员共享”只适用于 CM-HUB 内部仓库工作台。
5. 每次操作仍记录仓库用户和工作站，确保多人共享数据时可以追溯是谁处理了哪个包裹。
6. 若不同上游客户推送了相同扫描单号但对应不同面单，系统必须阻断自动匹配并提示冲突，不能因为数据全局共享而随机选择。

#### 14.3.5 单机应急模式仍存在的唯一同步限制

实体包裹不会同时出现在两台电脑前，因此业务已接受断网时不执行云端占用防重。但 B 断网后只能使用断网前最后一次同步到本机的拦截版本：如果 A 在 B 断网期间新增拦截单号，B 无法立即获知，这是网络物理限制而不是重复包裹问题。

单机应急界面必须持续显示：

- “当前为离线应急模式”的高可见状态；
- 最后一次共享批次和拦截名单同步时间；
- 当前缓存是否完整；
- 待回传打印事实数量；
- 恢复连接按钮。

D1–D7 均已确认并进入开发。生产上线前仍必须单独完成 `007`、`008` 迁移预演、备份、管理员登录验证、多工作站并发打印验收和明确的发布授权。
